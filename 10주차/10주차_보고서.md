## 2. 역할별 주요 수행 내용

### 2.1 역할 A — 네트워크 소켓 코어 (`proxy.py`)
- TCP 바이트 스트림에서 헤더 끝(`\r\n\r\n`)과 `Content-Length` 본문 길이를 기준으로 완전한 HTTP 요청 1건을 수신하는 `recv_request()` 구현
- 프록시 요청 형식(`GET http://host/path`)을 Origin 웹 서버 규격(상대 경로 + `Connection: close`)으로 변환하는 `build_upstream_request()` 구현
- 잘못된 요청(`400`), 미구현 HTTPS `CONNECT`(`501`), 업스트림 연결 실패(`502`), 타임아웃(`504`)에 대한 표준 HTTP 에러 응답 송신(`send_error()`) 및 단일 접속 릴레이 뼈대 완성

### 2.2 역할 B — HTTP 프로토콜 파서 및 필터 (`http_parser.py`)
- 수신된 원시 HTTP 요청 바이트에서 Request-Line을 파싱해 `method`, `host`, `port`, `url`, `is_blocked`를 딕셔너리로 반환하는 `parse_http_request()` 구현
- `set` 자료구조 기반 $O(1)$ 검색으로 유해 사이트(`warning.or.kr`, `game.com`, `gambling.com`) 접속을 판별하는 `BLACKLIST` 필터 로직 구현

### 2.3 역할 C — 바이트 기반 LRU 캐시 엔진 (`lru_cache.py`)
- 해시맵(`dict`)과 센티넬 노드(`_head`, `_tail`) 기반 이중 연결 리스트를 결합해 `get()` / `put()` 모두 $O(1)$에 동작하는 `LRUCache` 구현
- 단순 항목 개수가 아닌 **전체 바이트 상한(`max_bytes`) 및 단일 항목 상한(`max_item_bytes`)** 기준으로 가장 오래 사용하지 않은(LRU) 응답부터 축출하는 로직 구현
- 캐시 키 정규화(`make_key`, `key_from_url`) 및 캐시 가능 여부 검증 함수 `is_cacheable()` 구현
  - `GET` 요청 + `200 OK` 응답만 허용
  - `Cache-Control: no-store / private / no-cache` 및 `Set-Cookie` 포함 응답 제외
  - `Content-Length` 길이 일치 및 `Transfer-Encoding: chunked` 종료 시퀀스(`0\r\n\r\n`) 검증으로 잘린 응답 저장 방지

### 2.4 역할 D — 다중 접속 제어 프로토타입 및 초기 성능 검증 도구 (`server.py`, `bench.py`, `heavy_site.py`)
- **`server.py` (멀티스레드 프록시 프로토타입)**
  - `MultiThreadedHTTPProxyServer`에서 클라이언트 접속마다 워커 스레드(`threading.Thread`)를 생성해 병렬 처리하고, `threading.BoundedSemaphore`로 동시 실행 스레드 수 상한을 제어
  - `ThreadSafeProxyManager`에서 `cache_lock`과 `stats_lock`을 분리하고 `with` 구문으로 임계 영역을 보호해 **경쟁 상태(Race Condition)와 교착 상태(Deadlock)를 방지**
  - 팀원 A·B·C 코드 병합 전에도 단독 실행·실험이 가능하도록 Fallback 모듈과 플러그인형 함수 주입 인터페이스 구성
- **`bench.py` (3-모드 초기 벤치마크 스크립트)**
  - 60ms 인위적 네트워크 지연을 부여한 모의 Origin 서버(`SimulatedOriginWebServer`)를 대상으로 **단일 스레드 vs 멀티스레드 vs 멀티스레드 + LRU 캐시** 3가지 시나리오의 총 처리 시간, 처리량(RPS), 평균 지연시간, 캐시 적중률을 자동 비교 측정
- **`heavy_site.py` (체감 속도 비교용 로컬 테스트 사이트)**
  - 약 100KB SVG 이미지 카드 12개와 500ms 서버 지연·청크 분할 전송을 시뮬레이션하는 테스트 웹 서버를 제작해 브라우저에서 캐시 전/후 로딩 체감 속도를 확인할 수 있는 기반 마련

### 3.2 초기 3-모드 동시성 및 캐싱 벤치마크 (`python bench.py`)
- **실험 조건**: 총 요청 30건(인기 페이지 5종 반복), 동시 접속 10, 모의 Origin 서버 기본 RTT 지연 60ms

| 실행 시나리오 | 총 소요 시간 | 처리량 (Throughput) | 평균 지연시간 | 캐시 적중률 |
| :--- | ---: | ---: | ---: | ---: |
| 1. Single-Thread (No Cache) | `2.150 s` | `13.96 req/s` | `610.57 ms` | `0.0%` |
| 2. Multi-Thread (No Cache) | `0.203 s` | `148.07 req/s` | `66.75 ms` | `0.0%` |
| 3. Multi-Thread + LRU Cache | `0.081 s` | `370.17 req/s` | `23.47 ms` | `66.7%` |

## 4. 주요 이슈 및 설계 검토 사항

1. **모듈 간 입출력 인터페이스 차이 확인**
   - 팀원별 독립 개발 결과, 역할 B(`http_parser.py`)는 `dict` 형식을 반환하는 반면 역할 D 프로토타입(`server.py`)은 5-튜플을 가정하고 있었으며, 역할 C(`lru_cache.py`)는 항목 개수가 아닌 **바이트 용량(`max_bytes`, `max_item_bytes`) + `is_cacheable()` 정책** 기반으로 설계되었다.
   - 각 팀원의 원본 모듈을 최대한 수정하지 않고 결합할 수 있도록 차주에 **호환 어댑터 계층**을 도입하기로 정리했다.
2. **LRU 조회(`get`) 연산의 쓰기 동시성 고려**
   - `LRUCache.get()`은 캐시 적중 시 해당 노드를 이중 연결 리스트의 맨 앞(MRU)으로 이동시키므로 단순 읽기가 아닌 **쓰기 연산**이다. 따라서 `put()`뿐 아니라 `get()` 호출도 반드시 Mutex `Lock`으로 보호해야 데이터 구조 손상을 막을 수 있음을 확인하고 동기화 규칙에 반영했다.
